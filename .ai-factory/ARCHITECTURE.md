# Архитектура: Слоистая (Layered Architecture)

## Обзор

Слоистая архитектура разделяет код на горизонтальные слои, где каждый слой зависит только от слоя непосредственно под ним. Это самый простой архитектурный паттерн: минимум формализма, быстрый старт и достаточная защита от «спагетти-кода» — смешивания ввода-вывода, логики и состояния в одной функции.

Для этого репозитория выбор обусловлен назначением: учебные крейты-примеры с низкой сложностью домена. Каждый пример должен читаться сверху вниз, а не требовать понимания портов и адаптеров. При росте примера до полноценного проекта паттерн эволюционирует в Структурные модули без переписывания логики.

## Обоснование решения

- **Тип проекта:** учебный репозиторий с независимыми крейтами-примерами
- **Стек:** Rust (edition 2024), без фреймворков, БД и HTTP
- **Ключевой фактор:** один разработчик, минимальная сложность домена, приоритет — читаемость и скорость итераций

## Шаблон структуры крейта

Корень репозитория — набор независимых крейтов (одна директория = один пример). Внутри каждого крейта:

```text
tetris/                       # крейт-пример
├── Cargo.toml
└── src/
    ├── main.rs               # точка входа: композиция слоёв, игровой цикл
    ├── model/                # МОДЕЛЬ: чистое состояние и типы домена
    │   ├── mod.rs
    │   ├── board.rs          # поле, фигуры, их инварианты
    │   └── piece.rs
    ├── logic/                # ЛОГИКА: правила и трансформации состояния
    │   ├── mod.rs
    │   ├── movement.rs       # перемещение/поворот фигур
    │   └── scoring.rs
    └── render/               # ПРЕЗЕНТАЦИЯ: вывод в терминал, ввод
        └── mod.rs
```

Мелкие примеры (до ~200 строк) допустимо держать в одном `main.rs`; слои выделяются модулями `model/`, `logic/`, `render/` при первом же росте файла.

## Правила зависимостей

Зависимости направлены строго вниз: `main → render/logic → model`.

- ✅ `logic` использует типы `model`
- ✅ `render` читает состояние `model` (через `&`-ссылки)
- ✅ `main` знает про все слои и собирает их вместе (композиционный корень)
- ❌ `model` импортирует `logic` или `render` — модель ничего не знает о верхних слоях
- ❌ `logic` импортирует `render` — логика не выполняет ввод-вывод и не печатает в терминал
- ❌ циклические зависимости модулей

## Взаимодействие слоёв

- **Модель** — структуры данных с методами-инвариантами (`Board::can_place`, `Board::lock_piece`); никакого ввода-вывода
- **Логика** — по возможности чистые функции `fn step(state: &mut Board, input: Input)`; состояние передаётся параметрами, глобального изменяемого состояния нет
- **Презентация** — единственное место с `println!`/терминальным вводом; рендерит снимок модели, не мутирует её
- **main** — игровой цикл: опросить ввод → вызвать логику → отрисовать; содержит только склейку, не правила игры

## Ключевые принципы

1. **Направленность зависимостей вниз** — нижний слой никогда не импортирует верхний; это проверяется на этапе компиляции порядком `mod`-объявлений
2. **Богатая модель** — инварианты и правила защищаются методами модели, а не проверками снаружи
3. **Чистая логика** — трансформации состояния без побочных эффектов тестируются юнит-тестами `#[cfg(test)]` без заглушек
4. **Тонкий main** — точка входа только связывает слои; бизнес-правил в `main.rs` нет
5. **Минимум зависимостей** — учебный пример подключает внешние крейты (crates.io) только когда без них цель примера недостижима

## Примеры кода

### Богатая модель vs «мешок данных»

```rust
// ✅ ХОРОШО: инвариант защищён внутри модели
impl Board {
    /// Фигуру нельзя заблокировать вне границ поля.
    pub fn lock_piece(&mut self, piece: &Piece) -> Result<(), LockError> {
        if !self.can_place(piece) {
            return Err(LockError::Collision);
        }
        for (x, y) in piece.cells() {
            self.cells[y][x] = Some(piece.kind());
        }
        Ok(())
    }
}

// ❌ ПЛОХО: проверки снаружи, модель беззащитна
// в logic/mod.rs:
if board.is_free(x, y) {          // правило живёт вне модели —
    board.set(x, y, kind);        // любой новый вызов может его обойти
}
```

### Направление зависимостей

```rust
// src/logic/movement.rs — ✅ логика знает только модель
use crate::model::board::Board;
use crate::model::piece::Piece;

pub fn try_move(board: &Board, piece: &Piece, dx: i8, dy: i8) -> Option<Piece> {
    let moved = piece.offset(dx, dy);
    board.can_place(&moved).then_some(moved)
}

// src/render/mod.rs — ✅ презентация только читает модель
use crate::model::board::Board;

pub fn draw(board: &Board) {
    for row in board.rows() {
        println!("{row}");
    }
}

// ❌ ПЛОХО: render импортирует logic (и наоборот) — слой «в бок» или вверх
```

## Антипаттерны

- ❌ **God main** — весь пример в одной функции `main`: ввод, правила и отрисовка вперемешку; при росте файла выделять `model/`/`logic/`/`render/`
- ❌ **Печать из логики** — `println!` внутри `logic/` или `model/`; ввод-вывод только в `render/` и `main`
- ❌ **Анемичная модель** — публичные поля без методов-инвариантов; правила игры разбредаются по вызывающему коду
- ❌ **Глобальное изменяемое состояние** — `static mut`/`lazy_static` для состояния игры; состояние передаётся параметрами
- ❌ **`unwrap()` в не-тестовом коде** — для ожидаемых ошибок `Result`/`?`; паника допустима только для действительно неисправимых состояний
- ❌ **Зависимости между крейтами-примерами** — `tetris` не должен зависеть от другого крейта-примера; общее при необходимости выносится в отдельный крейт-библиотеку
