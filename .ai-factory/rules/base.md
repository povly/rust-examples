# Базовые правила проекта

> Соглашения, автоматически обнаруженные при анализе кодовой базы. Редактируйте по мере необходимости.

## Соглашения об именовании

- Файлы: snake_case (`main.rs`, будущие модули — `game_state.rs` и т.п.)
- Переменные: snake_case (стандарт Rust)
- Функции: snake_case (стандарт Rust)
- Типы/трейты: PascalCase (стандарт Rust)
- Константы: SCREAMING_SNAKE_CASE (стандарт Rust)
- Крейты: нижний регистр без подчёркиваний (`tetris`)

## Структура модулей

- Корень репозитория — набор независимых крейтов-примеров: одна директория = один пример (`tetris/`)
- Внутри крейта: `src/` с `main.rs` (или `lib.rs`), модули объявляются через `mod`
- Артефакты сборки (`target/`) и `Cargo.lock` для бинарных крейтов не редактируются вручную

## Обработка ошибок

- Проект в начальной стадии; при появлении кода — идиоматичный Rust:
- `Result<T, E>` + оператор `?` для распространяемых ошибок
- `Option` вместо nullable-значений
- `expect`/`unwrap` — только в тестах и примерах, где ошибка очевидно неисправима
- Пользовательские типы ошибок через `thiserror`/enum при росте сложности

## Поток управления

- Предпочитайте плоский, читаемый поток управления глубоким вложенным условиям. Используйте guard-условия, ранние `return`/`continue`, небольшие именованные функции-помощники или явную логику классификации, когда это делает код понятнее. Обрабатывайте граничные случаи и нерелевантные ветки рано, чтобы основной путь оставался видимым.

## Логирование

- На данный момент используется только `println!` в шаблонном коде
- При появлении реального логирования: крейт `log` + фасад (например, `env_logger`), уровень через переменную окружения `RUST_LOG`

## Тестирование

- Встроенный механизм: модули `#[cfg(test)]` с `#[test]`-функциями рядом с тестируемым кодом
- Запуск: `cargo test` внутри директории крейта
